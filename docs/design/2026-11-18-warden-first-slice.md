# Warden First Slice Implementation Plan

> **Superseded in part (2026-11-18):** Warden no longer writes Claude Code deny rules or hooks into `.claude/settings.json`. They ship as the Claude Code plugin in this repository; see the README.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A standalone `warden` CLI that compiles normalized rule records into an ESLint pass and Claude Code deny rules, ratchets every Guardrail from a baseline, detects tampering through a lock, and is adopted by Context Manager.

**Architecture:** A new repository `~/Code/warden` holds the schema, compiler, runner, emitters, the `core` pack, and an ESLint plugin. A consuming project keeps everything in `.warden/`. `warden check` runs Warden's own ESLint pass (generated config, inline config off) plus `legacy` command Guardrails on changed files, compares results with the baseline, and records Evidence.

**Tech Stack:** Node 25, TypeScript 5.9 (ESM), `commander` 12, `yaml`, `ajv`, ESLint 9 with `typescript-eslint` 8, Vitest 4.

**Spec:** [`2026-11-18-warden-guardrail-framework-design.md`](2026-11-18-warden-guardrail-framework-design.md). Tracking epic `cm-wkqedr`.

## Global Constraints

- Warden's own source contains no comments except the allowlist: `/// <reference`, `@vitest-environment`, and the `@generated` header. It runs its own `no-comments` Guardrail on itself from Task 4 on.
- Every finding is an error. No warnings anywhere.
- Raise errors explicitly. No silent fallbacks.
- Tool-owned paths: `.warden/` in a project; `~/.warden/` per machine (`evidence/<project>.jsonl`, `cache/<project>/`).
- Generated file header, first line, exactly: `@generated by warden <version> from <sourceHash> sha256:<contentHash>`, written in the target format's comment syntax.
- Exit status `0` means pass, `1` means a Guardrail failed, `2` means a usage or record error.
- Test workers capped at two: `vitest run --maxWorkers=2`.
- Every tool is reached through an adapter (`src/adapters/`). No module outside an adapter imports ESLint, TypeScript's compiler, or spawns a tool.
- Build carefully: one task at a time, a fresh implementer and an independent reviewer per task, and the next task starts only after the reviewer passes the previous one.
- Out of scope for this slice: Unit and Capability records, `warden where`, `fix`, `dispute`, `review`, `new`, mutation (`hollow`) runs, signature verification, the `principles` and style packs, `model` and `runtime` kinds, Codex and git-hook emitters.

## Review Focus

1. **A record file with a YAML syntax error or an unknown field.** Expect exit 2 naming the file and field, never a crash or a silently ignored field. Test in Task 1.
2. **A file deleted on the branch that has baseline entries.** Expect its entries to drop from the baseline, not a "file not found" failure. Test in Task 6.
3. **`warden check` outside a git repository, or with a base ref that does not exist.** Expect exit 2 with the ref named. Test in Task 6.
4. **A `legacy` command that hangs.** Expect it stopped at its budget, reported `over-budget`, exit 1. Test in Task 3.
5. **The cache when the Guardrail version changes but the file does not.** Expect a fresh run, not the old result. Test in Task 6.

## Record shapes (decided here, used by every task)

```ts
type Kind = "lint" | "type" | "model" | "runtime" | "review" | "instruction" | "legacy";
type Tier = "edit" | "commit" | "boundary";
interface Term { id: string; definition: string; bans: string[] }
interface Guardrail {
  id: string; kind: Kind; runs: Tier[]; budgetMs: number; version: number;
  implementation: string; options?: unknown;
  mustFail?: string; mustPass?: string;
}
interface Practice {
  id: string; pack: string; statement: string; terms: string[];
  paths: string[]; conflictsWith: string[]; guardrails: Guardrail[];
}
interface Pack { id: string; layer: number; terms: Term[]; practices: Practice[] }
interface ProjectConfig {
  warden: string; project: string; base: string;
  packs: { id: string; paths: string[] }[];
  tierBudgetMs: Record<Tier, number>; loopBreakerRepeats: number;
}
interface RecordSet { config: ProjectConfig; packs: Pack[]; root: string }
```

`implementation` is `<adapter>:<tool rule>`: `eslint:<rule>` for `lint`, `tsc:<compiler flag>` for `type`, `cmd:<shell command>` for `legacy`. A `cmd` command runs in the project root with `WARDEN_PACK_DIR` set to the absolute folder of the pack that owns the Guardrail, bundled or local, so it can run a script shipped in the pack: `cmd:node "$WARDEN_PACK_DIR/bin/clones.mjs"`. Failures and next actions print the command after `export WARDEN_PACK_DIR=<folder, shell-quoted>;`, so it runs as printed. `warden doctor` resolves the variable and checks that each named pack file exists. Every file in a bundled or local pack's folder but `.DS_Store` is hashed into the lock, and so is every project file a `cmd` command runs in program position, through `cd`, npm scripts, and relative imports, plus the data files listed in the Guardrail's `sources`, under `./` keys. `options` passes the tool's rule options through unchanged. `mustFail` and `mustPass` are required for every kind, `legacy` included, and must run. The schema has no field that disables, excludes, or overrides a lower pack's Practice, so "higher layers only tighten" holds by construction.

### Task 6: Check: changed files, baseline ratchet, tamper checks, cache, evidence

**Files:**
- Create: `src/runner/changed.ts`, `src/runner/baseline.ts`, `src/runner/cache.ts`, `src/runner/evidence.ts`, `src/runner/feedback.ts`, and the `check` path in `src/cli/check.ts`

**Interfaces:**
- Consumes: everything above.
- Produces:
  - `changedFiles(root: string, base: string): string[]`: `git diff --name-only --diff-filter=ACMR <merge-base>...HEAD` plus staged, unstaged, and untracked files; throws `RecordError` when not a repository or `base` is unknown.
  - `type Baseline = Record<string, Record<string, number>>` (guardrail id, then file, then violation count), stored at `.warden/baseline.json`.
  - `applyBaseline(results: RunResult[], baseline: Baseline, scanned: string[], existing: (f: string) => boolean): { failures: Violation[]; next: Baseline }`: a file fails a Guardrail when its count exceeds the baseline count; a lower count lowers the entry; a deleted file's entries are removed.
  - `cacheKey(file: string, contentSha: string, g: Guardrail): string` (includes `g.id` and `g.version`); `readCache`/`writeCache` under `~/.warden/cache/<project>/`.
  - `appendEvidence(project: string, e: { at: string; kind: "fired" | "cost" | "tampered" | "stalled"; guardrail?: string; file?: string; status?: string; ms?: number; detail?: string }): void` to `~/.warden/evidence/<project>.jsonl`. Tests set `WARDEN_HOME` to a temp directory; the module reads `process.env.WARDEN_HOME ?? os.homedir() + "/.warden"`.
  - `runCheck(opts: { root: string; wardenRoot: string; paths?: string[]; rule?: string; format: "text" | "agent" | "json"; hook?: "claude" }): Promise<number>` returning the exit status.
  - `formatFeedback(failures: Violation[], set: RecordSet, format): string` in `src/runner/feedback.ts`. For each failure, grouped by file:
    ```
    FAIL <file>:<line>  <practice id>
      Rule:     <practice statement>
      Do this:  <first 15 lines of the Guardrail's mustPass example>
      Fix:      warden fix <file>            (only when the Guardrail declares a fixer)
      Why:      warden explain <practice id>
    ```
    and it always ends with exactly one `Next action:` line: `Next action: change the code at the lines above to match "Do this". Do not edit .warden/ or generated config; that is recorded as tampering.` When the loop breaker trips, the next action is instead: `Next action: this failure repeated <n> times. Rewrite the code to follow "Do this", or file warden dispute <guardrail> <file> listing the approaches you tried. Stopping without either is recorded as stalled.` A tamper failure's next action is `revert your change to <file>`. Output never contains the words "blocked" or "cannot proceed". `json` emits the same fields as objects. With `--hook claude`, output is the Claude Code hook JSON `{"decision":"block","reason":<agent text>}` on failure and nothing on pass, so the agent sees the feedback right after the edit that caused it.

`runCheck` order: (1) tamper checks: each generated file's hash equals the lock (`tampered`, detail `generated-drift`); the lock on `base` (read with `git show <base>:.warden/lock.json`, skipped when absent) has no Guardrail missing from the current lock, no raised `budgetMs`, and the base baseline has no entry the current baseline exceeds (`tampered`, detail `loosened`); (2) run Guardrails on changed files (or `paths`), using the cache; (3) apply the baseline and write `next`; (4) append `fired` and `cost` Evidence; (5) print feedback with `formatFeedback`, including the loop-breaker line `Same failure <n> times: fix the code to match the compliant example.` when the same guardrail, file, and content hash failed `loopBreakerRepeats` times in the Evidence log.
